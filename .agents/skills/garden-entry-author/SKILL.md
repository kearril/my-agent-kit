# Garden Entry Author（花园条目写作与修订规程）

## 一、 三大不可逾越的执行铁律

1. **事实必有出处，严禁臆测与幻觉**
   - 严禁脱离真实资料编写条目。涉及外部开源项目、框架、资源或工具时，必须通过网络检索或直接查阅官方 GitHub 仓库（源码、README、Release 日志）、官方文档等一手资料进行核对。
   - 正文开头必须明确标注该条目收录时的官方版本号或调研时间节点。

2. **严格执行两阶段确认，绝不擅自修改文件**
   - 在未获得用户明确许可前，单轮对话内严禁直接修改或新建条目文件。
   - 必须遵循：**查验资料 $\to$ 生成大纲供审核 $\to$ 用户确认 $\to$ 输出完整草稿供审核 $\to$ 用户明确同意写入 $\to$ 写入并构建验证** 的闭环流程。

3. **原生遵循深度去 AI 味文风**
   - 必须严格执行 `references/style-guide.md` 中的全部文风、节奏与排版准则，保持中文母语者的技术书面语质感，坚决杜绝翻译腔与模板化套路。

---

## 二、 动态规程路由机制

动工前按需读取对应参考文件，严禁凭印象操作：

1. **文风与排版把控**：必读 `references/style-guide.md`；
2. **元数据与标签核验**：必读 `references/frontmatter.md`；
3. **条目类型专属骨架**：
   - 处理 `type: skill` 时，必读 `references/types/skill.md`；
   - 处理 `type: project` 时，必读 `references/types/project.md`；
   - （其他类型的骨架规范将在后续实践中逐步沉淀）。

---

## 三、 标准工作流闭环

```text
1. 事实调研 ──── 检索/阅读官方一手资料，核实版本、功能边界、运行机制与资产清单
      ↓
2. 生成大纲 ──── 提炼条目定位，撰写规范，适用范围，生成条目大纲供用户审核
      ↓
3. 撰写草稿 ──── 对照 style-guide 与对应 type 规范编写完整草稿（含 Frontmatter）
      ↓
4. 用户授权 ──── 提交草稿，等待用户明确确认同意写入（如“同意”、“确认写入”）
      ↓
5. 精准写入 ──── 执行文件写入或编辑，确保无格式破损与多余空白
      ↓
6. 最低验证 ──── 在终端运行 `pnpm test && pnpm build`，确保测试通过且构建路由无误
```
