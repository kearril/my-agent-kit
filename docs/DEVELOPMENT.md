# 开发纪律

这份文档规定代码、内容、依赖和 Git 如何被持续维护。AI 如何参与任务见 `docs/AI-WORKFLOW.md`；文档总入口见 `docs/README.md`。

## 1. 先确认边界

开始实现前确认：

- 改动要解决的问题
- 允许修改和明确不修改的范围
- 验收标准以及需要用户确认的风险

涉及技术栈、内容模型、首页结构、部署、视觉系统或无障碍方向时，先在 `docs/DECISIONS.md` 留下决定、原因和影响，再实现。

## 2. 内容与数据

新增或修改条目时，检查以下内容是否完整且有意义：

- 类型是否正确
- 摘要是否能独立说明条目价值
- 标签是否使用已有词汇，是否确实需要新标签
- 外部资产地址是否可访问，并且有清晰的链接名称
- 关联条目是否仍然存在
- `updatedAt` 是否需要更新

如果字段发生变化，必须同步修改 `docs/CONTENT.md` 和内容集合的 schema。

## 3. Astro 与 React 的边界

- 页面结构、静态内容和服务端生成优先使用 Astro。
- 只有需要浏览器端状态、事件监听或浏览器 API 的局部区域才使用 React Island。
- 不把整个网站做成客户端 React 应用。
- Content Collections 是内容的唯一事实来源；组件中不重复维护同一份条目数据。
- 交互组件要考虑键盘操作、焦点状态、Esc 关闭和移动端尺寸。

## 4. 依赖管理

- 统一使用 pnpm。
- 修改依赖后必须提交 `package.json` 和 `pnpm-lock.yaml` 的对应变化。
- 新增依赖前先确认现有 Astro、Tailwind 或浏览器能力不能满足需求。
- 实验性依赖要在决策记录中写明用途、风险和移除条件。
- 升级核心依赖后至少运行一次 `pnpm build`。

## 5. 验证要求

每次完成一个可交付改动后，至少运行：

```bash
pnpm build
```

涉及交互时，还要在桌面和移动端检查：卡片打开与关闭、筛选重置、加载更多、键盘操作和滚动锁定。涉及视觉时，检查长标题、空状态、无图条目和窄屏布局。

视觉实现必须遵守 `docs/DESIGN.md`。新增组件不能直接采用第三方组件库的默认圆角、渐变、模糊阴影或灰色主题；交付前按设计规范中的检查清单逐项确认。

## 6. Git 纪律

- `main` 始终保持可构建、可部署。
- 较大的功能使用独立分支开发，完成后再合并。
- 提交信息使用清晰的动作开头，例如 `add`、`update`、`fix`、`refactor`、`docs`。
- 不提交密钥、个人隐私、构建产物或本地环境文件。
- 不使用强制重置、强制推送等可能覆盖历史的操作，除非明确确认影响范围。

## 7. 文档职责

- `README.md`：项目入口、安装和常用命令。
- `AGENTS.md`：编码代理的全局规则，保持短小并作为唯一权威入口。
- `docs/README.md`：文档导航、权威来源和更新规则。
- `docs/AI-WORKFLOW.md`：AI 辅助开发的任务流程、证据纪律和质量门槛。
- `docs/DEVELOPMENT.md`：开发规则和质量门槛。
- `docs/DESIGN.md`：俏皮野兽派视觉、组件、动效和无障碍规范。
- `docs/DEPLOYMENT.md`：部署决策和上线清单。
- `docs/CONTENT.md`：条目类型、字段和标签约定。
- `docs/DECISIONS.md`：经过讨论确认的长期决策。

同一规则只保留一个权威位置。发现旧文档与当前实现不一致时，优先修正文档，不让矛盾继续累积。文档只在能够减少重复错误或解释长期取舍时新增，不为一次性任务建立永久规则。
